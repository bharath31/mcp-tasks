# Poppy integration seam (experimental)

Framework-neutral server helpers for verified Auth0 Poppy identities and a subset of the Operations v3 API/MCP wire format. This is **not a Poppy implementation or a conformant storefront**. Poppy 1.0 is a draft, and Operations v3 is newer than the 0.3 documentation of the upstream API PR. Neither real SDK compatibility nor a live tenant has been verified here. Do not advertise the extension until the application implements and tests all obligations described below.

## Install and verify

From the repository root run `npm ci`, then `npm ci --prefix integrations/poppy`, `npm --prefix integrations/poppy run build`, and `npm --prefix integrations/poppy test`. The root install supplies TypeScript, tsx and Prettier; the package lock pins the structured-fields parser. `npm --prefix integrations/poppy run format:check` checks formatting. Tests inject SDK-shaped fixtures; they do not verify cryptographic proofs.

## SDK compatibility and trust boundary

Stable `@auth0/auth0-api-js` 1.7.0 and `@auth0/nextjs-auth0` 4.33.0 do not include the relevant open PR APIs. This package does not depend on or vendor them. Research was against `auth0/auth0-auth-js` PR #342 at `5cd394aefe4a1e99373a1ddd26fa28c8be3c2e71` (`ApiClient.verifyPoppyRequest`) and `auth0/nextjs-auth0` PR #2939 at `58d631efcf1329c700a20c78369eeb6edad45beb` (`auth0.poppy.getContext()` / `getSession()`). These are unreleased, subject to change, and need separately built, pinned SDKs and tenant support; presence of a method is not proof of compatible behavior or of protocol 1.0 support. Review the pinned source and its build instructions before attempting compatibility work. There is no automatic fixture fallback, no shipped upstream crypto, and no live-mode claim. Missing methods cause actionable errors. In particular Next.js PR's `getContext` can return `human` when Poppy is disabled: callers **must** set `poppyConfigured: true` only from trusted server configuration that actually enabled and initialized Poppy, never from a request or environment that has not been checked. The flag is an operator assertion, not SDK feature detection.

`verifyApiRequest(client, request, resolve)` calls the injected SDK verifier with the request method, URL and headers; a Poppy header forces `requireSession`. It returns `unauthenticated` if there is no verified Poppy session, including a verified ordinary bearer token; use a separately verified human-auth flow if needed. It never decodes JWTs or promotes arbitrary `act` to a human. `normalizeBrowserContext(auth0, resolve, {poppyConfigured: true})` calls the server-side SDK context and session directly; do not pass browser JSON. Both return an `Actor` with distinct kinds `unauthenticated`, `human`, `guest-agent`, `signed-in-agent`; agents have `agentId`, `pairwiseUserId`, `sessionId`, and only signed-in agents have `customerId`. Scopes come only from verified token/context, are empty for guests, and should be enforced by the merchant service. Merchant-defined scope names: `cart:write`, `checkout:write`, `addresses:read`, `orders:read`.

`resolve(verifiedId, source)` must consult a trusted, explicitly configured allow-list and map **each** header CIMD URL, token-derived agent identity, and browser `act.sub` to the same canonical merchant agent ID when they represent the same accepted agent; return undefined otherwise. Do not use unverified input or accept all IDs. The upstream header allow-list does not cover every token/browser context. The application owns accurate alias registration, verifier configuration/audience/origin, and session expiration/revocation. `canLinkGuest` requires the same canonical agent, pairwise user and session and a newly verified customer; cart IDs and body values are never evidence. `sameOperationPrincipal` instead compares agent, pairwise user and (for signed-in sessions) customer across sessions; it never permits guest/account crossover.

## Operations and discovery

`buildDiscovery` builds the narrow 1.0 API-only document; it never advertises UCP or website operations. `validateDiscovery` validates this supported subset, not arbitrary Poppy documents. Only set `operationsV3` when the merchant actually supports v3 on the advertised interfaces, including durable approval checks and at-most-once execution. Validate `Poppy-Version` and negotiate `Poppy-Extensions` with `operationsNegotiated` before returning an operation. Unknown/malformed extension declarations negotiate nothing; missing/unsupported versions throw `version_unsupported` (the HTTP layer must map that to 400). `parseApprovalHeader` and `parseMcpApproval` parse transport data only. Unknown fields cannot grant assurance. `approver=user` and `approver=agent` are both **agent-attested**, never merchant-witnessed customer approval. High-risk actions need an independently verified customer flow on a merchant-owned page; `merchantReviewAlternative` limits links to a configured exact HTTPS origin. Do not place tokens or secrets in those URLs.

`createOperation` snapshots immutable JSON terms. `approvalRequired` / `approvalDeclined` produce API 403 results; `mcpApprovalRequired` / `mcpApprovalDeclined` return native tool errors. The application must itself bind the original interface and principal, exact request and revision, enforce expiry and current authorization/scopes, preserve durable operation and idempotency state, prevent double execution and reconcile uncertain provider results. These helpers do **not** do those business checks, perform approvals, issue links, or ensure that a caller negotiated the extension. Never use an agent approval as a direct-customer ceremony. MCP Tasks is optional and not replaced here. If UCP is integrated later, its `requires_escalation` / `continue_url` flow must replace, not stack with, Operations approval for UCP checkout.

## Evidence and limits

Included tests use mocked SDK results and local protocol fixtures only. No `createTestAgent` upstream compatibility suite, real signed-request test, Next.js browser join, live Auth0 tenant, conformance suite, UCP, website-operations endpoint, or production commerce service was run. Discovery and Operations helpers implement only the explicitly documented subset and cannot establish protocol conformance. Treat every upstream SDK update and 1.0 protocol change as requiring renewed compatibility/security review.
