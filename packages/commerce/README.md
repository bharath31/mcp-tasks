# Commerce domain prototype

This single-host domain prototype includes server-priced carts, quotes and an order execution ledger. It is **not a production storefront**: there is no HTTP handler, authenticated request verifier, CSRF protection, upstream revocation integration, full Task Authority adapter, durable real provider, deployment, or production approval verifier. Node 22's `node:sqlite` is experimental. Do not expose these methods directly to untrusted clients.

`createCartStore(path, options)` requires callers to supply a freshly verified actor on every call. Human actors are `{kind: "human", customerId, scopes: []}`; agents are `{kind: "agent", customerId?, agentId, pairwiseUserId, sessionId, scopes}`. These fields must come from trusted server-side verification, never JSON. Guest linking requires exact agent/user/session continuity, a verified customer ID, and `cart:write`. Account cart agents need `cart:write`; quote and execution agents need `checkout:write` and `addresses:read`. Human review requires ownership, a human session and a separate operation-bound proof callback. An agent cannot be a human reviewer; a human cannot execute an agent-originated checkout. Session grants, local disconnect and upstream revocation must be enforced by the host's verifier on every call.

## Quotes and accounts

The `customerAccount` option must implement `getAddress(customerId, addressId)` returning a trusted `{id, customerId, label, version, trustedForAgentCheckout, destination}` or null. Destination is a JSON object. The provided `createFixtureCustomerAccountPort()` is synthetic and is never automatically selected. Quotes are immutable 15-minute snapshots of catalog prices, destination/version and zero demo tax/shipping. Each cart has a stable operation ID across revisions. After completed execution, a new `createQuote` on that cart starts a new purchase/operation; do not call it for a mere retry. A processing operation blocks cart changes and new quotes. `getQuote` returns historical terms; `validateQuote` checks current identity, scopes, cart/version, latest revision, prices, expiry and trusted address. New dispatch requires current terms. A previously claimed execution can be reconciled or replayed after expiry or later cart changes, but only after authorizing its immutable customer, agent and scopes; that path never places another order.

A conservative built-in floor requires customer verification for totals above $50, untrusted destinations, or a destination changed between revisions; otherwise agent confirmation is required. The injected authorization port can deny or raise this requirement but cannot lower it. Quote `requirement` shows this floor, not a final policy decision. Real merchant taxes, shipping, pricing, risk policy and account data require integration work.

## Execution and approval boundaries

`authorization.evaluate({actor, quote})` must return `agent_confirmation`, `customer_verification`, or `denied`. No adapter means refusal. Low-risk agent checkout additionally requires `verifyAgentConfirmation({actor, quote}) === true`, an injected server-side verifier for an operation/revision-bound protocol confirmation, not arbitrary request JSON. `recordHumanReview(quoteId, verifiedHuman)` requires an injected `verifyHumanReview({actor, quote}) === true`; that callback must independently verify fresh human presence bound to exact quote/operation/revision/customer and terms. Browser session, agent assertion, Poppy `approver=user` and body assurance fields are not proof. The host must provide origin/CSRF protection and securely bind verification context to the request. The review is persisted for that exact revision. `getHumanReview` is historical, not proof that current conditions still hold. Callbacks and policy are security boundaries; an unsafe implementation defeats the checks.

`orderProvider.place({quote, idempotencyKey})` submits the exact snapshot, and `orderProvider.reconcile({quote, idempotencyKey})` performs **read-only** authoritative lookup. Provider methods return `{id}` on confirmed success; null, malformed results or exceptions remain processing. The operation ID is the stable provider idempotency key. SQLite atomically inserts one processing claim before place. Replays never resubmit; explicit `reconcileQuote` can resolve an unknown outcome and never calls place. A crash before provider submission remains processing on an unknown lookup. An authoritative provider may return `{status: "absent"}`, which is exposed as `provider_confirmed_absent` but does not itself release the claim. Optional `atomicAbandonAbsent` is a security-critical adapter: it must atomically prove absence, permanently fence every late provider submission for the key, and mark the same execution abandoned in the same durable transaction. Without that contract, abandonment is unavailable. Never infer absence from a timeout and never retry a real provider blindly. The provider must honor the key durably across crashes/processes, and return an authoritative stable order ID for the exact immutable terms. SQLite alone cannot guarantee provider exactly-once effects. Order result persistence is local; there is no order-history HTTP API.

The external account lookup is not atomic with the SQLite claim or provider submission. The merchant/provider contract must coordinate address mutations with dispatch, or independently reject execution when the version/snapshot has changed. This prototype cannot enforce external atomicity. A point-in-time quote validation is not a lock on the account service. Implementing a real provider without that contract is unsafe.

`createFixtureAuthorization("fixture")` and `createFixtureOrderProvider("fixture")` are explicitly simulated: the former exposes test-only confirmation/review controls and the latter only creates in-memory fake orders, never charges. Fixture provider state does not survive its own process restart. Never wire fixtures into a live deployment. `createCartStore` never selects fixture or live adapters automatically.

Run `npm --prefix packages/commerce run build`, `npm --prefix packages/commerce test`, and `npx --no-install prettier --check packages/commerce`. The build is a JavaScript syntax check, not a TypeScript build.

Quotes issued before the sticky destination-verification flag are historical only: validation, completion, human review and normal reconciliation refuse them with `legacy_quote_requires_requote` before calling adapters. `getQuote` and `getHumanReview` remain historical reads, not execution authorization. Create a fresh quote to derive the destination requirement from stored operation history. If a legacy checkout is already processing, a fresh quote is blocked; investigate its provider outcome manually rather than resubmitting or interpreting absence as failure.
