# Commerce cart and quote milestone (incomplete)

This is not a storefront or checkout implementation. No HTTP handler, authentication verifier, authorization, approval, order, payment or reconciliation is implemented. Do not use it for purchasing or as a production security boundary.

`createCartStore(path)` opens a single-host SQLite ledger. Callers must verify every actor using their own trusted server-side authentication and construct actor objects from the verifier, never request JSON. Agents use `{kind: "agent", agentId, pairwiseUserId, sessionId, customerId?, scopes}` and humans use `{kind: "human", customerId, scopes: []}`. Guest agents have no customerId. An account agent needs merchant-defined `cart:write` for account cart access or linking. Guest linking requires an exact verified agent/user/session tuple and a customer ID, and is atomic and idempotent. A human cannot claim a guest cart. Signed-in humans may access their own carts. IDs are not credentials. Account agents remain bound to the original agent and pairwise user; their session may change after linking.

Catalog prices are server-owned; cart input may contain only productId and bounded integer quantity. SQLite provides cross-process write serialization on one host; it is not a distributed ledger. `:memory:` is useful only for tests. The actor verifier, account identity lifecycle and local disconnect/revocation handling are not implemented here. Never expose these methods directly to untrusted clients.

Run `npm --prefix packages/commerce run build` and `npm --prefix packages/commerce test` with Node 22.13 or later. The built-in SQLite module is experimental in Node 22.

## Quotes (not executable)

Pass `createCartStore(path, { customerAccount })`, where the trusted merchant adapter provides `getAddress(customerId, addressId)` and returns `{ id, customerId, label, version, trustedForAgentCheckout, destination }` or null. Destination is a JSON object holding fulfillment data. `createFixtureCustomerAccountPort()` is synthetic demo data, never a live default. A missing account adapter fails closed. `createQuote(cartId, verifiedActor, shippingAddressId)` creates an immutable 15-minute server-priced snapshot with zero demo tax and shipping. The destination and its version are copied into the quote. Each cart has a stable operation ID and monotonically increasing revision; this incomplete milestone cannot finish a purchase or start a new purchase on the same cart.

Agents need `checkout:write` and `addresses:read` and must match the cart's customer, agent and pairwise user. Humans need the authenticated customer session and ownership. `getQuote` reads historical terms; `validateQuote` additionally checks latest revision, expiry, current cart version/catalog prices and the current trusted address. Both require the same verified actor/scope checks. All quote requirements are `denied`: there is no authorization policy, approval or completion. Client-supplied prices, destination details and risk flags are not accepted. No customer-address HTTP endpoint exists.

Address lookups are external to the SQLite transaction. Validation is a point-in-time check, not an atomic promise that an external account record cannot change after it returns. A future execution path must recheck and coordinate merchant account state with dispatch and must not treat `validateQuote` alone as approval or a durable execution claim. SQLite and the trusted account adapter are assumed protected from unauthorized writes. There is no verifier, revocation integration, HTTP CSRF protection, or multi-host correctness claim.

## Non-executable human review record

`recordHumanReview(quoteId, verifiedHuman)` is a partial review primitive, **not an authorization, approval, or execution claim**. The supplied actor must originate from a trusted verifier, and must be a human customer owning the quote. An agent is always rejected. The optional server-injected `verifyHumanReview({ actor, quote })` callback must independently verify a fresh human ceremony bound to that exact quote ID, operation ID, revision, customer and immutable terms, using server-side proof context. It must return exactly `true` only after successful verification. It must not trust request JSON, an agent assertion, actor fields as proof, or an unbound browser session. No verifier is configured by default; missing verification refuses. Request/CSRF/origin verification and how the callback obtains authenticated operation-bound proof are merchant integration responsibilities and are not implemented here. A permissive or incorrectly bound callback defeats this primitive. No production or fixture proof verifier is provided.

The record is stored in SQLite only after revalidating the quote both before and after the callback and rechecking local terms within the insertion transaction. `getHumanReview` returns a historical record to the owning human, even when its quote has since become stale; it is not evidence that current conditions still hold. Address state is external and can change after its last lookup, including while the SQLite transaction executes. No existing or future provider should treat this record as sufficient to charge: execution will additionally require fresh policy authorization, a fresh exact-terms check, an atomic durable execution claim, and provider-specific idempotency and reconciliation. Any merchant/provider integration must define how to handle external address mutations between verification and dispatch; the local SQLite ledger cannot make external systems atomic. There is no such integration in this package.
