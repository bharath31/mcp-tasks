# Interoperability and trust boundaries

Status: **experimental**. Task Authority is this repository's custom approval backend, embedded in the default Worker or separately deployed with Node—not an Auth0 product. This page states what has been shown to work, against what, and where each guarantee stops. It is the evidence behind the README's positioning, so update it when that evidence changes.

## MCP Tasks conformance (spec `2026-07-28`, extension `io.modelcontextprotocol/tasks`)

| Behaviour                                                              | Refund Desk (`demo/refund-desk`)                                | Policy Desk (`demo/policy-desk`, live demo)                                   | SDK `renderMcp`               |
| ---------------------------------------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------- |
| `server/discover` advertises the tasks extension, one protocol version | Yes                                                             | Yes                                                                           | n/a                           |
| `tools/call` returns `CreateTaskResult` only to declaring clients      | Yes; `-32021` otherwise                                         | Yes; `-32021` otherwise                                                       | n/a                           |
| `tasks/get`                                                            | Yes                                                             | Yes; resumes eligible work through a claim and idempotent simulator           | n/a                           |
| `tasks/update`                                                         | Yes; answers to unknown, answered or superseded keys ignored    | Acknowledged and ignored: Policy Desk never asks the client for input         | n/a                           |
| `tasks/cancel` acknowledged with an empty `complete` result            | Yes; withdraws unclaimed authority, never claims a reversal     | Yes; withdraws unclaimed authority, a claimed refund reports its real outcome | n/a                           |
| `-32021` for `tasks/*` from a non-declaring client                     | Yes                                                             | Yes                                                                           | n/a                           |
| If present, `Mcp-Name` must equal `params.taskId`                      | Enforced                                                        | Enforced                                                                      | n/a                           |
| `input_required` with form elicitation                                 | Exception note (`exception_note`, re-asks `exception_note:<n>`) | Not used                                                                      | Not used                      |
| `input_required` with URL elicitation (owner approves on hosted page)  | `owner_approval:<approvalId>`                                   | Not used (reviewers approve in the Reviews page)                              | `owner_approval:<approvalId>` |
| Input-request keys unique over the task's lifetime                     | Yes (regression test with the official requester)               | n/a                                                                           | Yes, one key per approval     |
| `notifications/tasks`, `subscriptions/listen`                          | Not implemented (method not found); clients poll                | Not implemented; clients poll                                                 | n/a                           |
| `tasks/list`, `tasks/result`                                           | Not found (not in this spec revision)                           | Not found                                                                     | n/a                           |
| `ttlMs` and `cacheScope` on `tools/list` results                       | Yes                                                             | Yes                                                                           | n/a                           |

Policy Desk requires `tasks/get` or an explicit run request to drive approved work; it has no independent worker loop. Refund Desk does have a durable task worker. Policy Desk's advertised 24-hour task TTL does not override its 15-minute sandbox expiry/cleanup.

An elicitation answer of `accept` never approves anything. It only says the user went to the page; the decision is made and verified by Task Authority.

## Auth0-signed `approve()` proofs

The SDK approval page, OIDC round trip, real post-login Action module, Policy Desk MCP task mapping, and Task Authority proof bridge run against the local HTTPS OIDC fixture and local Postgres. Tests cover valid and rejected decisions, wrong approvers, self-approval, proof replay, expiry, and Task Authority FGA denial. These tests exercise the project code and fixture; they do not establish behavior on a live Auth0 tenant. Live Auth0 passkey/nonce behavior remains unverified for this experiment; CIBA `authorization_details` also needs a suitably entitled/configured tenant.

The test commands are `npm run test:unit`, `node --import tsx --test --test-concurrency=1 demo/policy-desk/tests/approve-mode.test.ts`, and `node --import tsx --test auth0/tests/integration/approval-proof.test.ts`.

Inngest, Temporal, and Vercel adapters are structural integrations. Their real local-engine suites have not been run because the engine packages and local services are not installed; see [the approval documentation](approve.md) for the limits of each adapter.

## Claude Code

Tested on 2026-10-24 with Claude Code 2.1.310 on its v2 MCP runtime, which negotiated `2026-07-28` with `server/discover`. The server was Refund Desk on the local stack (`npm run interop:claude-code`), with a bearer token from the local identity provider in the MCP config, so Claude Code's own OAuth sign-in was not exercised. Every request and response was captured by a logging proxy in front of `/mcp`. Runs were in a Linux container with `CLAUDE_CODE_ENTRYPOINT=cli`: an interactive session in a terminal multiplexer, and `claude -p --input-format stream-json` with `CLAUDE_AUTO_BACKGROUND_TASKS=1`. A macOS terminal was not tried.

| Flow                                                                  | What Claude Code did                                                                                                                                                                                                                                 | Result        |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| Automatic refund (policy allows)                                      | Declared the tasks extension on every request, got `CreateTaskResult`, polled `tasks/get` every `pollIntervalMs` (5 s), gave Claude the `completed` result                                                                                           | Pass          |
| Manager approval (task stays `working`)                               | Kept polling while the status message carried the approval link; a manager approved at the service; the refund ran once and Claude reported it                                                                                                       | Pass          |
| Exception note (`input_required`, form elicitation), interactive      | Showed the server's form; answered `exception_note` once through `tasks/update` with `{ action: "accept", content: { note } }`                                                                                                                       | Pass          |
| Owner approval (`input_required`, URL elicitation), interactive       | Showed the URL with **Open in browser**, **I'm done, continue** and **Decline**; answered `owner_approval:<approvalId>` once with `{ action: "accept" }`; the local fixture then submitted simulated passkey evidence; the simulated refund ran once | Pass          |
| Any `input_required` in a headless run                                | Sent `tasks/cancel` at once, as its docs say; the server withdrew the request before any authority or money moved                                                                                                                                    | As documented |
| Owner approval with `OWNER_APPROVAL_PROMPT=status`, headless          | Task stayed `working` with the approval link in `statusMessage`; the owner approved out of band; the refund ran once                                                                                                                                 | Pass          |
| A Claude Code on the web session (the cloud container's own settings) | Did not declare the extension; `request_refund` was refused with `-32021`                                                                                                                                                                            | As designed   |

Fixed after the first runs, in the same change that added this section:

- `tools/list` results lacked `ttlMs` and `cacheScope`, which `2026-07-28` requires; Claude Code filled in defaults and logged it.
- The `-32021` message was the bare "Missing required client capability". Claude Code passes only the message to the model, which then guessed at the cause; it now names the tasks extension.
- Completed results did not say how the refund was authorized, and Claude told the user that no approval had been needed when the owner had approved with a passkey. Results now carry `authority.approval` (`required`, `approvalId`, `status`, `ownerMayApprove`) and the exception note.
- Policy Desk put a path, not a URL, in `statusMessage`; hosts show it outside the page (`/tasks`), so it is now absolute.
- Headless hosts cancel tasks that ask for input, which would withdraw every owner approval in `claude -p`, Agent SDK and GitHub Actions runs. `renderMcp(outcome, { ownerPrompt: "status" })` and Refund Desk's `OWNER_APPROVAL_PROMPT=status` keep the task `working` and point the owner at the page instead.

Not covered: Claude Code's OAuth sign-in against Auth0 (dynamic client registration or `--client-id`, and the `resource` parameter), resuming a session while a task runs, and Policy Desk.

## Trust boundaries

| Boundary                                   | Trusted to                                              | Enforced there                                                                                                                                                                                                                                                                                                                                                                                                                                            | Not protected                                                                                                                                                      |
| ------------------------------------------ | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Agent / MCP client → app                   | Ask for work within its delegation                      | OAuth bearer for the MCP audience; task access bound to the caller (unknown and foreign ids look identical); tool and `tasks/update` schemas carry no approval field                                                                                                                                                                                                                                                                                      | A prompt-injected agent can ask for anything the delegation and policy allow: bound it with policy                                                                 |
| App → Task Authority                       | State business facts; run the side effect after a claim | M2M client permissions, split between the API client and the executor; a forwarded user must be a signed human token, and an `act` or `ai_agent` token is refused as a grantor; canonical arguments and business-state version are digest-bound; facts are stored separately and checked on registration replay                                                                                                                                           | A lying app: facts are assertions, replayed exactly but not verified. A forwarded token's DPoP binding is not re-checked: the app must verify it before forwarding |
| Person → Task Authority (approval)         | Decide one exact operation                              | Human token only: client credentials, `act` (delegated) and `sub_profile: ai_agent` tokens are refused on every channel (REST, batch, CIBA, lease, challenge); policy-specific assurance (session MFA or operation-bound challenge/RAR); replay checks for operation tokens; DPoP where required; eligible DPoP rejection without another factor; FGA eligibility re-read; separation of duties, or owner self-approval with a passkey when policy allows | A reviewer's own compromised, freshly stepped-up session                                                                                                           |
| Task Authority → Auth0 and FGA             | Prove identity; answer "may they, now"                  | JWT issuer, audience and JWKS checks; FGA checked on every decision and claim with `HIGHER_CONSISTENCY`; outages fail closed                                                                                                                                                                                                                                                                                                                              | A removal racing a claim by the length of one check                                                                                                                |
| Executor → payment provider                | Move money once per authorized operation                | A claim before dispatch; the operation key as the provider idempotency key; after an uncertain claim, look the payment up by key (`reconcile_required`)                                                                                                                                                                                                                                                                                                   | A compromised worker that holds provider credentials. **One authorization is not exactly-once execution**: that needs provider idempotency and reconciliation      |
| Executor → Task Authority (outcome report) | Say what happened                                       | Reports are evidence, never authority. A lost or failed report is `unknown` and leads to reconciliation, never a recorded failure                                                                                                                                                                                                                                                                                                                         | A lying executor: `not_submitted` releases a claim, so the provider key is the real double-pay defence                                                             |

These are logical boundaries. Policy Desk co-locates app and backend with a shared runtime database role; the separate Node deployment can isolate credentials. See [security-model.md](security-model.md) for storage, cleanup, attacker assumptions and known limits.

## Auth0 MCP adapter scope

This repository does not depend on `@auth0/ai-mcp` or `@auth0/ai-fastmcp`. Refund Desk already uses `@auth0/auth0-api-js` for resource-server authentication; Policy Desk has its own JWT/DPoP integration. Upstream adapters could reduce authentication plumbing, but adopting one would not replace this custom backend's policy, durable approval records or claim-time checks. Any adoption must be tested against the `2026-07-28` discovery/Tasks contract; it is not an implemented integration or a compatibility promise.
