# Security model

Applies to the _reference implementation_ of a **proposed** service. It is not a security review, and nothing here is a statement about shipped Auth0 behaviour.

## What the service guarantees (and the test that shows it)

| Guarantee                                                                    | Mechanism                                                                                                                                                             | Evidence                                                                              |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Identity is never taken from a body                                          | Tenant from token issuer; humans only via signature-verified tokens; `.strict()` schemas have no user/tenant fields                                                   | `tests/service/lifecycle.test.ts` (auth, forged org, cross-tenant), `tests/contracts` |
| Authority is explicit and bounded                                            | Delegation: owner type, agent, scope, actions, resource prefixes, numeric ceilings, expiry (max 48h), immutable provenance (DB trigger)                               | lifecycle + security tests                                                            |
| User-owned authority ends when the user's rights end                         | Owner permission re-read from FGA at every claim                                                                                                                      | `4a`, security "initiator loses the permission"                                       |
| Organization-owned authority survives the initiator but not the org's policy | Agent registration + org policy checked; former employee loses read access                                                                                            | `4b`                                                                                  |
| An approval covers exactly one operation                                     | Digest binds tenant, org, delegation, key, action, scope, resource, canonical arguments (integer minor units), business-state version; approval row stores the digest | digest golden vector; changed amount/destination tests; `5`                           |
| A human decision is authentic                                                | Fresh MFA `amr`, `auth_time` after the request and within 5 min, `authorization_details` bound to approval id + digest, single-use `jti`                              | "assurance is enforced", "replay" tests                                               |
| The approver is eligible _now_                                               | FGA re-read at decision **and** at claim; approver != initiator/grantor                                                                                               | `2`, wrong-manager, self-approval tests                                               |
| Dispatch authority is checked at the dispatch boundary                       | One transaction: delegation, operation digest, state version, approval, FGA, then claim insert                                                                        | `claims.ts`; security suite                                                           |
| At most one logical authorization                                            | Partial unique index on live claims; recovery returns the same claim; after lease/revocation the answer is `reconcile_required`                                       | concurrency (8 parallel workers), lost response, crash tests                          |
| Revoke and claim serialize                                                   | Both take the delegation row lock first                                                                                                                               | race A/B tests with a latch inside the lock                                           |
| Dependency failure fails closed                                              | FGA/datastore errors map to retryable `authorization_unavailable` with nothing claimed                                                                                | FGA and datastore outage tests                                                        |
| Nothing secret is logged or audited                                          | Audit field allow-list rejects names like token/secret; evaluated by test over all rows and logs                                                                      | "audit never contains tokens"                                                         |
| Audit is append-only                                                         | DB triggers reject UPDATE/DELETE                                                                                                                                      | storage test                                                                          |
| The customer cannot touch service tables                                     | Separate datastore; role without grants gets `42501`                                                                                                                  | role privilege test                                                                   |

## Attacker assumptions and outcomes

| Attacker                                | Attempt                                                                                       | Outcome                                                                                                                  |
| --------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Prompt-injected agent                   | Passes `approved: true` or another user's id                                                  | Tool/`tasks/update` schemas have no such field; forged `inputResponses` keys are ignored; claim stays `approval_pending` |
| Agent with a task id                    | Reads/cancels another user's task                                                             | Same "Task not found" for unknown, other user, other org (byte-identical error)                                          |
| Southridge manager                      | Approves a Northstar refund                                                                   | `not_authorized`, indistinguishable from an unknown approval id; recorded in audit for investigators                     |
| Requester                               | Self-approves, even if given the approver relation                                            | `approver_ineligible: initiator_cannot_approve`                                                                          |
| Agent owner                             | Approves their own agent with `self_approval: owner`                                          | Allowed only with a fresh WebAuthn step-up bound to this approval and digest; never for quorum or org-owned agents       |
| Agent owner                             | Switches clients (MCP to REST/CLI) to skip the approval                                       | Same operation, same approval: policy and the claim check live in Task Authority, not in the transport                   |
| Approver                                | Replays a decision token on another approval                                                  | `token_replayed`                                                                                                         |
| Agent with a reviewer's delegated token | Approves with a token carrying `act` or `sub_profile: ai_agent`, even with fresh MFA and DPoP | `invalid_identity: agent_cannot_approve` on every channel (REST, batch, CIBA, lease, challenge), audited                 |
| Customer bug / forged policy            | Asserts "no approval needed" for $150                                                         | Tenant guard raises the requirement to human                                                                             |
| Racing workers                          | Claim the same operation concurrently                                                         | One claim; the rest recover it                                                                                           |
| Crashed worker                          | Dies after claim, before the provider call                                                    | After the lease: `reconcile_required`; provider looked up by key; one refund                                             |
| Operator                                | Tries `/operator/*` without a token or outside demo mode                                      | 401 / not mounted (404)                                                                                                  |
| Anyone                                  | Forges a warehouse event                                                                      | Uniform 401 for bad signature, schema, or timestamp; duplicates apply once                                               |
| Another origin                          | Browser calls the service                                                                     | CORS only for an explicit allow-list                                                                                     |

## Revocation and claim ordering

Revocation committed before a claim denies it. A claim committed before revocation stands: the service reports the operation as **in flight** and any retry becomes `reconcile_required`. It never reports a claimed operation as stopped, and `tasks/cancel` after dispatch is acknowledged without claiming reversal.

## Known limits (read these)

1. **A compromised customer worker holding provider credentials can bypass the service.** The provider adapter refuses to act without a minted grant, but that is an in-process control. Credential scoping at the provider (restricted keys, per-operation tokens) is outside this prototype.
2. **The service trusts customer business facts** (amount, currency, destination) as assertions. It binds and replays them exactly; it cannot know they are true.
3. **Outcome reports are unverified customer attestation.** A report that is lost after the side effect committed is sent as `unknown` and settled by reconciliation, never recorded as a failure. `not_submitted` releases a claim; a lying executor can obtain a second claim (the provider idempotency key and metadata lookup are the real defense against double payment).
4. **FGA freshness is the length of one check.** The service keeps no cache and sends every check with `HIGHER_CONSISTENCY`, which bypasses Auth0 FGA's short-lived check cache, so removal takes effect on the next call; a removal racing a claim may lose by the duration of that call.
5. **Rate limiting is per process.** Quotas (open delegations/approvals, claims/day) are enforced in the database; the request-rate limit is in memory.
6. **Not verified live:** Auth0 login/MFA/OBO/RAR/CIBA, Auth0 FGA SaaS, Stripe test mode, any mainstream MCP client. Those flows are exercised only against a local standards-shaped OIDC provider, which shares my assumptions about the protocol and so cannot catch a wrong one.
7. **Not reviewed:** no external security review, no fuzzing, no load or soak testing, no key rotation procedure, no retention job (audit and idempotency rows are never deleted by this code; retention must outlast possible replay and is not configured here).
8. The reviewer page uses `auth0-spa-js` with in-memory token storage; it was driven in real Chromium against the local provider (approve, reject, ineligible reviewer) and has not been tested against a real tenant.
9. **CIBA orphaned grants:** if the provider releases the token but the service cannot verify or record it (for example the authorization check is unavailable), the single-use grant is gone and authorizes nothing. The approval can only expire and recovery is a new request (tested).
10. **A forwarded subject's DPoP binding is the backend's to check.** When a trusted backend forwards a user token in `X-Task-Authority-Subject`, the service verifies its signature and claims but not a DPoP proof for its `cnf.jkt`: the backend must verify the binding before forwarding, as Policy Desk does. Delegated tokens (`act`, `sub_profile: ai_agent`) are refused as grantors (`grantor_must_be_human`) and as reviewers (`agent_cannot_approve`).
11. Request bodies are capped (128KB service, 256KB app) and the operator token is compared in constant time.
