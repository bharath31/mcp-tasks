# Stillroom Supply

A fictional customer shopping reference for Action Authority. The shop and its artwork are illustrative. No real purchases, identity, Poppy browser join, or payment integration are implemented here.

## Run

From the repository root run `npm ci`, `npm ci --prefix examples/storefront`, and `npm --prefix examples/storefront run build`. Then from `examples/storefront` run `SHOPPING_FIXTURE=1 NODE_ENV=production npm run fixture` and open **http://127.0.0.1:3187**. Node 22.13+ is required for SQLite. Use the explicit fixture controls to grant the agent account access, confirm a low-risk quote, or switch to a simulated customer for review, then resume the fixture agent. No real identity, customer verification, Poppy proof, charge or payment occurs. `SHOPPING_FIXTURE_DB` selects the local SQLite file (default `fixture.sqlite`); its contents are demo data. Stop the process with Ctrl-C.

The fixture server binds only to 127.0.0.1, checks the actual socket peer and local address and exact Host, rejects forwarded headers, and requires exact same-origin on mutations. **Never expose it via a proxy, tunnel, shared host or public listener**: anyone with local access can act as the fixture customer. It is not a production authentication boundary. The standard Next `npm run dev` and `npm run start` do not activate it; their `/api` remains unavailable even if the fixture environment variable is set. `/?view=fixture` remains a separate non-interactive presentation. The fixture server is an explicit separate entry point, not a live-mode fallback.

## Integrating the merchant service

Keep your existing Auth0 tenant, catalog, cart, order and payment backend. Install an appropriate Auth0/protocol adapter and connect the commerce Fetch handler to Next route handlers under `/api`. The typed browser boundary is `lib/client.ts`; the local commerce implementation is in `packages/commerce/`. Wire real catalog imagery, address selection, account sign-in, human checkout and checkout status polling. Do not trust IDs or browser-provided identity. Guard the commit-to-order boundary with server-owned quotes, your existing risk rules, ownership checks, durable idempotency and payment reconciliation. Preserve ordinary human checkout.

The review route is `/review/[id]`: connect the backend's `reviewUrl` to it and provide a server-verifiable, operation-bound customer verification and CSRF/origin protection. The server must reject agent sessions even if they are signed in. The client button is not proof of presence. The sample checks a `directCustomerVerification` capability only to avoid offering an unavailable button; the server is the security boundary. Fixture approval must be unavailable in live mode and explicitly identified. Quote changes invalidate approval; completion must revalidate it. The UI retry reuses the same idempotency key only while this page is open; a production integration should persist the key safely across reloads.

Poppy browser support in upstream Next.js SDK PR #2939 is open, not a released SDK feature. This example does not call proposed methods. Inject a compatible verified adapter explicitly; otherwise report Poppy unsupported. Never fall back from live to fixture identity, issue development cookies as production authentication, or expose tokens and approval URLs to model text. Agent-attested confirmation is not merchant-witnessed approval. Full UCP is not implemented; do not advertise it. No tenant setup runs here.

The local simulator invokes the fixture HTTP service; it is not a connected personal agent. Fixture confirmation and customer review are simulated and bound server-side to the exact quote revision. A changed quote needs a fresh review, and retry reuses the operation; the durable fixture provider never charges. Product illustrations in `public/` are original simple SVGs made for this example, not photographs.

The additional integration contract includes `GET /api/addresses` returning server-owned `{ addresses: [{ id, label, trustedForAgentCheckout }] }` and `POST /api/carts/:id/link` with no identity fields in the body. Link only after verified continuity of agent ID, pairwise user ID and session ID, and account sign-in. The local fixture exercises `linkCart` only after its explicit simulated grant; real sign-in/continuity is not wired. Merchant-defined agent scopes are `cart:write`, `checkout:write`, `addresses:read`, and `orders:read`. Never accept raw addresses or client-provided trust flags. The live review button is deliberately unavailable until a merchant-owned verification ceremony is integrated.

Browser smoke test: start the production server on port 3187 (`npm run build && npm run start -- -p 3187`), then in another terminal run `CHROME_PATH=/path/to/chrome npm run test:browser`. The test intercepts API requests with test-only responses; it does not validate the commerce backend. It writes screenshots to `/tmp/storefront-{390,768,1440}.png`.

The normal Next catch-all `/api` route returns `503 shopping_unavailable` with `no-store` for every supported method. Only the separate loopback fixture server handles the API; it does not supply a production identity boundary. The storefront remains a separately locked install because it uses Next and React 19 while the existing root applications use React 18; root `npm ci` does not install it. From the root, run `npm ci --prefix integrations/poppy` before `npm run test:shopping`; that command also runs the real local fixture HTTP suite. For the separate real-backend browser smoke, start the fixture server on port 3187, then run `CHROME_PATH=/path/to/chrome npm run test:fixture-browser`. The older `test:browser` uses intercepted mocks, not the backend.

The fixture requires an `Idempotency-Key` header but the domain deliberately uses the server-owned operation ID as the provider key. A new operation is a new purchase even if a client reuses its header. Fixture sessions are in-memory and reset on server restart; the SQLite order/provider ledger survives, but a restarted agent session must grant account access again. The provider ledger models only deterministic local simulated orders, not payment reconciliation with an external provider.

For a processing fixture operation, `POST /api/checkouts/:id/reconcile` performs a read-only provider lookup. If it returns `provider_confirmed_absent`, `POST /api/checkouts/:id/abandon` atomically checks absence and fences late fixture placement in the same SQLite database; only then can the cart be requoted as a new operation. Unknown outcomes remain processing. These are fixture-specific semantics, not a recipe for recovering ambiguous external payments. The fixture's agent/customer pairwise identity is stable across process restart, while each guest session gets a distinct random session ID; existing linked carts require an explicit fixture grant after restart. Legacy unsafe snapshots still require manual investigation.
