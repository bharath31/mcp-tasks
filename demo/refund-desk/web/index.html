Refund Desk reference implementation

A customer's MCP Tasks refund workflow. Who may delegate, who may approve, and whether this exact refund is still authorized are decided by a separately deployed proposed Task Authority service, not by this application.

2. Copyable prompts

Create something to refund

Use create_test_payment with amountMinor 30000, currency USD and a new UUID idempotencyKey. Tell me the paymentId.

Automatic path: $50, no human

Use request_refund for order "N-50", payment <paymentId>, amountMinor 5000, currency USD, reason "Returned unopened". Then poll tasks/get until it completes.

Exception path: $150, needs a manager

Use request_refund for order "742", payment <paymentId>, amountMinor 15000, currency USD, reason "Customer returned the item", exceptionNote "Damaged on arrival, RMA verified". Give me the task id, then stop. I will check back later.

After you reconnect

Call tasks/get for task <taskId> and summarize the status, status message and result.

3. What happens

  1. The task is created durably and a scoped, expiring delegation plus the exact operation ($150.00 USD, payment, destination, digest) are registered with Task Authority. Status stays working while it waits for the warehouse; input_required is used only when the client can actually answer.
  2. A signed warehouse event arrives (a synthetic producer). The app asks Task Authority for a human decision. Close your MCP client now to see disconnected execution.
  3. The manager opens the review link, sees the exact operation, signs in with a fresh second factor bound to that operation, and decides. The service checks live FGA eligibility.
  4. The worker obtains an atomic authorize-and-claim immediately before the refund, calls the provider with the operation key as idempotency key, and reports the outcome. Reconnect and read the result.

Who owns what

Customer owns

  • MCP Tasks lifecycle and polling
  • Business eligibility and the $100 auto threshold
  • Provider credentials and the refund call
  • Reconciliation by operation key

Task Authority owns

  • Delegation lifetime and revocation
  • Exact-operation approvals and live FGA eligibility
  • One-use claim, replay and race semantics
  • The authoritative decision history

Existing Auth0 products

  • Login, MFA, organizations
  • @auth0/auth0-api-js token verification and OBO exchange
  • FGA relationship checks
